## Полиморфизм: одно действие, разное поведение

### Задача

Сервис оформления заказов предлагает три способа доставки:

- _Курьер_. Стоит 50 лей.
- _Почта Молдовы_. Стоит 35 лей.
- _Самовывоз_. Бесплатен.

Для курьера и почты доставка становится бесплатной, если сумма товаров составляет не менее 1000 лей. Сначала разработчик может хранить выбранный вариант в строке и вычислять цену через `match`:

```php
function deliveryCost(string $code, int $goodsTotal): int
{
    if ($code === 'pickup') {
        return 0;
    }

    if ($goodsTotal >= 1000) {
        return 0;
    }

    return match ($code) {
        'courier' => 50,
        'post' => 35,
    };
}

echo deliveryCost('courier', 600); // 50
```

Для маленькой задачи это допустимое решение. Проблемы начинаются не из-за самого `match`, а из-за того, что код способа доставки используется во многих местах.

Например,

- одной функции нужно название для страницы,
- другой - цена,
- третьей - ориентировочный срок.

Чтобы добавить экспресс-доставку, придётся изменять несколько функций. Ошибка в одной из них приведёт к тому, что разные части сайта будут понимать один и тот же код по-разному.

Есть и более тонкая ошибка. Вызов `deliveryCost('unknown', 1200)` вернёт `0`: функция завершится до `match` и даже не проверит существование способа доставки. А вызов с тем же неизвестным кодом и суммой 600 лей завершится `UnhandledMatchError`. Поведение неверных данных зависит от суммы заказа, хотя не должно.

Этот пример показывает две разные задачи:

- _Хранить правила каждого способа вместе_, чтобы не искать их по нескольким функциям.
- _Ограничить допустимые способы_, чтобы нельзя было передать произвольный объект или несуществующий вариант.

Сначала решим первую задачу с помощью объектов.

### Разные классы с одинаковыми методами

Для решения описанной выше проблемы можно использовать объектно-ориентированный подход. Вместо того чтобы хранить данные и действия отдельно, мы объединяем их в одной сущности - объекте. Таким образом, объект содержит не только данные, но и методы для работы с ними.

Пусть курьер (`Courier`) и самовывоз (`Pickup`) представлены отдельными классами. У каждого есть:

- `title()` для названия и,
- `cost()` для расчёта.

Но реализация методов различается.

```php
class Courier
{
    public function title(): string
    {
        return 'Курьер';
    }

    public function cost(int $goodsTotal): int
    {
        return $goodsTotal >= 1000 ? 0 : 50;
    }
}

class Pickup
{
    public function title(): string
    {
        return 'Самовывоз';
    }

    public function cost(int $goodsTotal): int
    {
        return 0;
    }
}

$deliveries = [new Courier(), new Pickup()];

foreach ($deliveries as $delivery) {
    echo $delivery->title() . ': ' . $delivery->cost(600) . " лей\n";
}
// Курьер: 50 лей
// Самовывоз: 0 лей
```

Посмотрим, что происходит на двух итерациях цикла:

1. В переменной `$delivery` находится `Courier`. PHP выполняет `Courier::title()` и `Courier::cost(600)`.
2. Затем там находится `Pickup`. Запись вызова не меняется, но PHP выполняет методы `Pickup`.

Внешнему коду (коду, который вызывает `cost`) не приходится спрашивать , курьер это или самовывоз. Он обращается к обоим объектам одинаково. Это и есть проявление _полиморфизма_.

**Полиморфизм (polymorphism)** - возможность вызывать один и тот же метод у объектов разных классов, при этом каждый класс определяет, как именно этот метод работает. Например, вызов `$delivery->cost(600)` возвращает `50` для курьера и `0` для самовывоза.

Когда появится четвёртая доставка, цикл по-прежнему будет вызывать `title()` и `cost()`. В этом польза полиморфизма: код, который _использует_ объекты, меньше зависит от числа их разновидностей.

Запустите [пример 01](code/demos/01_polymorphism.php). Обратите внимание, что полиморфизм работает уже здесь, без интерфейсов и наследования. Но от ошибок типов мы пока не защищены.

### Чего не хватает: общего требования к объектам

Допустим, мы вынесли вывод одной доставки в функцию:

```php
function deliveryLine($delivery, int $goodsTotal): string
{
    return $delivery->title() . ': ' . $delivery->cost($goodsTotal) . ' лей';
}
```

Функция предполагает, что ей передадут подходящий объект. Однако её параметр `$delivery` не ограничен типом. В него можно передать неподходящий объект, у которого вообще нет метода `cost()`. Ошибка возникнет только тогда, когда PHP попытается вызвать отсутствующий метод внутри функции.

Проверять каждый вариант через `if ($delivery instanceof Courier)` тоже неудобно: _при добавлении нового способа придётся изменять функцию_. Нам нужен один тип, который объединяет разные способы доставки не по родителю или формуле расчёта, а по обязательным возможностям. Такой тип можно объявить _интерфейсом_.

## Интерфейсы

### Интерфейс как контракт

**Интерфейс (interface)** - тип, который описывает требования к классам:

- какие открытые методы они должны предоставлять,
- какие у этих методов параметры и результаты.

Интерфейс задаёт _что_ объект умеет, но не определяет, _как_ он это делает[^1].

_Синтаксис_

```php
interface InterfaceName
{
    public function action(int $value): string;
}

class Example implements InterfaceName
{
    public function action(int $value): string
    {
        return (string) $value;
    }
}
```

В объявлении интерфейса метод записан без тела. Ключевое слово `implements` означает, что класс _обязуется его реализовать_. Параметры и тип результата должны быть совместимы с интерфейсом, а сам метод должен быть `public`. В таком смысле интерфейс называют _контрактом (contract)_.

Запишем общий интерфейс для любого способа доставки:

```php
interface DeliveryMethod
{
    public function title(): string;
    public function cost(int $goodsTotal): int;
}
```

Его требования вполне конкретны:

- `title()` не принимает аргументов и возвращает название доставки как строку.
- `cost(int $goodsTotal)` принимает сумму товаров в леях и возвращает стоимость доставки как целое число.

Создадим самовывоз и экспресс-доставку. Экспресс стоит 120 лей при любой сумме товаров, а самовывоз бесплатен:

```php
final class PickupDelivery implements DeliveryMethod
{
    public function title(): string
    {
        return 'Самовывоз';
    }

    public function cost(int $goodsTotal): int
    {
        return 0;
    }
}

final class ExpressDelivery implements DeliveryMethod
{
    public function title(): string
    {
        return 'Экспресс-доставка';
    }

    public function cost(int $goodsTotal): int
    {
        return 120;
    }
}
```

У обоих классов один интерфейс, но разные алгоритмы. Теперь функция может объявить требуемый тип:

```php
function deliveryLine(DeliveryMethod $delivery, int $goodsTotal): string
{
    return $delivery->title() . ': ' . $delivery->cost($goodsTotal) . ' лей';
}

echo deliveryLine(new PickupDelivery(), 1200) . "\n";
echo deliveryLine(new ExpressDelivery(), 1200);
// Самовывоз: 0 лей
// Экспресс-доставка: 120 лей
```

Функция принимает любой объект, реализующий `DeliveryMethod`. Ей не важно, содержит ли он скидки, фиксированную стоимость или другое правило. Чтобы добавить доставку дроном, достаточно написать новый класс с `implements DeliveryMethod`. Переписывать `deliveryLine()` не требуется.

### Что PHP проверяет и чего интерфейс не гарантирует

Интерфейс не служит простым комментарием. PHP использует его при проверке классов и аргументов функций[^1]:

- _При объявлении класса_. PHP проверяет, что обязательные методы реализованы и их объявления совместимы с интерфейсом. Отсутствующий метод или несовместимый тип результата приводят к ошибке.
- _При вызове функции_. Если параметр объявлен как `DeliveryMethod`, объект неподходящего типа приводит к `TypeError` ещё при передаче аргумента.
- _При проверке `instanceof`_. Выражение `$delivery instanceof DeliveryMethod` показывает, реализует ли объект этот интерфейс.

_Важно_: совпадение имён методов само по себе недостаточно. Даже если `BicycleDelivery` содержит `title()` и `cost()`, без `implements DeliveryMethod` его нельзя передать в `deliveryLine()`. PHP проверяет явно объявленный тип, а не угадывает намерения по именам методов.

При этом интерфейс не гарантирует правильную бизнес-логику. Класс может объявить `cost()` с нужным типом `int`, но возвращать `-500` или неправильно считать скидку. _Интерфейс проверяет форму взаимодействия, а корректность расчёта нужно проверять отдельно._ Поэтому при разработке нужно отдельно проверять расчёты, в частности границу бесплатной доставки.

Исполняемый пример с `instanceof` находится в [файле 02](code/demos/02_interfaces.php).

### Несколько интерфейсов: один класс, несколько ролей

До сих пор нам был нужен один тип `DeliveryMethod`: функция расчёта должна получить название доставки и узнать её цену. Но теперь появилось другое требование. Для некоторых доставок пользователь может узнать номер отслеживания, а для других такой возможности нет. Самовывоз, например, не предполагает отслеживания посылки в пути.

Можно было бы добавить `trackingNumber()` прямо в `DeliveryMethod`. Но тогда самовывозу пришлось бы реализовать метод, который для него не имеет смысла. Лучше описать отслеживание отдельным интерфейсом:

```php
interface DeliveryMethod
{
    public function title(): string;
    public function cost(int $goodsTotal): int;
}

interface Trackable
{
    public function trackingNumber(): string;
}
```

Таким образом, `DeliveryMethod` описывает расчёт доставки, а `Trackable` - возможность получить номер отслеживания. Они не обязаны использоваться вместе.

Рассмотрим три класса. Курьерская доставка поддерживает обе возможности. Самовывоз умеет рассчитывать стоимость, но не имеет трек-номера. Отдельная посылка хранит номер отслеживания, но не является способом доставки и не рассчитывает цену:

```php
final class CourierDelivery implements DeliveryMethod, Trackable
{
    public function __construct(private string $number) {}

    public function title(): string
    {
        return 'Курьер';
    }

    public function cost(int $goodsTotal): int
    {
        return $goodsTotal >= 1000 ? 0 : 50;
    }

    public function trackingNumber(): string
    {
        return $this->number;
    }
}

final class PickupDelivery implements DeliveryMethod
{
    public function title(): string
    {
        return 'Самовывоз';
    }

    public function cost(int $goodsTotal): int
    {
        return 0;
    }
}

final class Parcel implements Trackable
{
    public function __construct(private string $number) {}

    public function trackingNumber(): string
    {
        return $this->number;
    }
}
```

Теперь код может запрашивать только ту возможность, которая ему действительно нужна:

```php
function trackingLine(Trackable $item): string
{
    return 'Отслеживание: ' . $item->trackingNumber();
}

$courier = new CourierDelivery('MD12345');
$pickup = new PickupDelivery();
$parcel = new Parcel('MD67890');

echo trackingLine($courier) . "\n"; // Отслеживание: MD12345
echo trackingLine($parcel);          // Отслеживание: MD67890
```

Функция `trackingLine()` не знает, работает ли она с курьерской доставкой или с отдельной посылкой. Она требует только `Trackable`. А `$pickup` нельзя передать в эту функцию: класс не реализует данный интерфейс. При этом функция `deliveryLine(DeliveryMethod $delivery, ...)` принимает курьера и самовывоз, но не посылку.

| Класс             | `DeliveryMethod` | `Trackable` |
| ----------------- | ---------------- | ----------- |
| `CourierDelivery` | Да               | Да          |
| `PickupDelivery`  | Да               | Нет         |
| `Parcel`          | Нет              | Да          |

Один класс может реализовать несколько интерфейсов через запятую после `implements`. Каждый интерфейс описывает отдельную роль объекта. Это удобно, когда разные части программы нуждаются в разных возможностях, и не заставляет все классы иметь лишние методы. Полный пример находится в [файле 04](code/demos/04_roles.php).

## Абстрактные классы: общий алгоритм для родственных объектов

### Когда одного интерфейса мало

Интерфейс `DeliveryMethod` уже позволяет использовать любой способ доставки. Но пока курьер и почта по отдельности содержат одинаковую проверку: если сумма товаров не меньше 1000 лей, доставка бесплатна. При изменении порога придётся исправлять оба класса. Если таких доставок станет десять, риск забыть одну реализацию увеличится.

Нельзя просто перенести расчёт в `DeliveryMethod`: интерфейс объявляет требования, а не готовое тело обычного метода. Можно создать общего родителя _именно для тех способов доставки, которые подчиняются одинаковому правилу_. Экспресс-доставка не подходит под это условие и останется самостоятельным классом.

**Абстрактный класс (abstract class)** - класс, объявленный с ключевым словом `abstract`, который нельзя создать напрямую, но от которого могут наследоваться другие классы[^2]. В отличие от интерфейса, в нём могут быть готовые методы, свойства и константы.

**Абстрактный метод (abstract method)** - метод, который объявлен без тела и должен быть реализован в неабстрактном наследнике.

_Синтаксис_

```php
abstract class BaseClass
{
    abstract protected function requiredStep(): int;

    public function result(): int
    {
        return $this->requiredStep();
    }
}
```

Здесь `requiredStep()` не имеет реализации. У неабстрактного наследника обязательно должен появиться совместимый метод. Напротив, `result()` уже реализован, поэтому наследники могут пользоваться им без повторения кода. Абстрактные методы бывают `public` или `protected`, но не `private`: наследник должен иметь возможность их реализовать.

### Общий расчёт и отдельные шаги

Назовём родительский класс `RegularDelivery`: он представляет только обычные доставки, у которых есть порог бесплатности. Общее правило запишем в методе `cost()`, а базовую цену каждый наследник предоставит через `baseCost()`.

```php
abstract class RegularDelivery implements DeliveryMethod
{
    public const FREE_FROM = 1000;

    abstract public function title(): string;
    abstract protected function baseCost(): int;

    final public function cost(int $goodsTotal): int
    {
        if ($goodsTotal >= self::FREE_FROM) {
            return 0;
        }

        return $this->baseCost();
    }
}

final class CourierDelivery extends RegularDelivery
{
    public function title(): string
    {
        return 'Курьер';
    }

    protected function baseCost(): int
    {
        return 50;
    }
}

final class PostDelivery extends RegularDelivery
{
    public function title(): string
    {
        return 'Почта Молдовы';
    }

    protected function baseCost(): int
    {
        return 35;
    }
}
```

Здесь появились сразу три важные связи:

- `RegularDelivery implements DeliveryMethod` - абстрактный класс обещает нужные методы интерфейса, но может оставлять часть реализации наследникам.
- `CourierDelivery extends RegularDelivery` - курьер наследует готовый алгоритм `cost()` и предоставляет отсутствующие шаги `title()` и `baseCost()`.
- `final public function cost(...)` - наследники не смогут заменить общий алгоритм своей версией. Это уместно, поскольку мы хотим сохранить одно правило бесплатной доставки.

Проследим за вызовом `(new CourierDelivery())->cost(600)`. Поскольку `CourierDelivery` не объявляет `cost()`, PHP находит готовый метод в `RegularDelivery`. Сумма 600 меньше порога 1000, поэтому код вызывает `$this->baseCost()`. Переменная `$this` указывает на объект курьерской доставки: выполнится именно `CourierDelivery::baseCost()`, который вернёт 50.

Для заказа на 1200 лей выполнение завершится раньше, на `return 0`. Метод `baseCost()` даже не понадобится. Таким образом, родитель определяет порядок действий, а наследник - значение, требующееся для одного из них.

```text
CourierDelivery::cost(600)
    |
    v
RegularDelivery::cost(600)
    |
    +-- 600 >= 1000 ? ---- да ---> 0
    |
    +-- нет ---> $this->baseCost() ---> CourierDelivery::baseCost() ---> 50
```

_Схема 7.1. Общий метод вызывает реализацию отдельного шага у конкретного объекта_

Такую организацию часто называют _шаблонным методом (template method)_: родитель задаёт алгоритм, а наследники реализуют отдельные его части[^3]. Сейчас важно не название шаблона, а практическая польза: правило порога хранится в одном месте.

Метод `baseCost()` объявлен `protected`, поскольку он нужен только родителю и наследникам. Пользователь страницы оформления должен обращаться к открытому `cost()`, а не к деталям расчёта. Попытка создать `new RegularDelivery()` завершится ошибкой, как и объявление неабстрактного наследника без обязательного `baseCost()`.

### Почему экспресс-доставка не наследует `RegularDelivery`

Вернёмся к классу `ExpressDelivery`, который мы уже написали в разделе об интерфейсах. Экспресс стоит 120 лей даже при сумме заказа 1200 лей. Если наследовать `RegularDelivery`, мы получим противоречие: родительский `cost()` вернёт ноль, а переопределить его не позволит `final`.

Правильнее не заставлять экспресс-доставку подчиняться чужому правилу. Она реализует `DeliveryMethod` напрямую, а курьер и почта используют одновременно `DeliveryMethod` и общего родителя:

```text
DeliveryMethod (title(), cost())
    |
    +-- RegularDelivery (общее правило от 1000 лей)
    |       +-- CourierDelivery (базовая цена 50)
    |       +-- PostDelivery    (базовая цена 35)
    |
    +-- PickupDelivery  (всегда 0)
    +-- ExpressDelivery (всегда 120)
```

_Схема 7.2. Общий интерфейс у всех доставок, общая реализация только у части из них_

Функция `deliveryLine(DeliveryMethod $delivery, ...)` работает со всеми четырьмя классами. Внутри неё нет ни проверок типов, ни особых условий для курьера. В [примере 03](code/demos/03_abstract.php) можно сравнить результаты для заказов на 600 и 1200 лей.

Здесь проходит важная граница: _интерфейс нужен для взаимозаменяемости, абстрактный класс - когда у нескольких родственных классов действительно есть общий алгоритм_. Иногда достаточно только интерфейса; не нужно добавлять абстрактный класс ради самого факта существования наследования.

_Небольшое задание._ Добавьте `EveningDelivery` - вечернюю доставку за 80 лей независимо от суммы товаров. Она должна реализовывать `DeliveryMethod`, но не наследовать `RegularDelivery`. Проверьте вызовы `deliveryLine(new EveningDelivery(), 600)` и `deliveryLine(new EveningDelivery(), 1200)`: в обоих случаях стоимость должна остаться 80 лей. Объясните, почему наследование от `RegularDelivery` здесь было бы ошибкой.

## Трейты: повторное использование небольшого поведения

### Общий код без общего родителя

Предположим, курьерская и почтовая доставки умеют сохранять текущий статус отправления: "создано", "в пути" или "доставлено". Для обеих нужны методы `send()`, `complete()` и `status()`. Они делают одно и то же, поэтому повторять их в каждом классе неудобно.

Можно вынести этот код в родительский класс, но статус - лишь одна из возможностей доставки. Например, курьер уже может наследовать класс с общим расчётом цены, а PHP не поддерживает наследование сразу от двух классов. Поэтому для небольшого одинакового поведения удобно использовать трейт.

**Трейт (trait)** - механизм, позволяющий использовать готовые методы и свойства в нескольких классах без создания общего родителя[^4]. Трейт объявляют словом `trait`, а подключают внутри класса через `use`.

_Синтаксис_

```php
trait TraitName
{
    public function example(): void
    {
        // Готовый код метода.
    }
}

class SomeClass
{
    use TraitName;
}
```

_Пример_

```php
trait HasDeliveryStatus
{
    private string $status = 'создано';

    public function send(): void
    {
        $this->status = 'в пути';
    }

    public function complete(): void
    {
        $this->status = 'доставлено';
    }

    public function status(): string
    {
        return $this->status;
    }
}

final class CourierDelivery
{
    use HasDeliveryStatus;
}

final class PostDelivery
{
    use HasDeliveryStatus;
}

$courier = new CourierDelivery();
$post = new PostDelivery();

$courier->send();
echo $courier->status() . "\n"; // в пути
echo $post->status();           // создано
```

Оба класса получили одинаковые методы, но объекты хранят состояние независимо. Вызов `$courier->send()` меняет только статус курьерской доставки. Почтовая доставка по-прежнему имеет статус "создано". Если в дальнейшем появятся дополнительные статусы, общую реализацию достаточно изменить в одном трейте.

В этом примере классы специально упрощены: мы рассматриваем только статусы, а не расчёт стоимости. В реальном классе можно одновременно наследовать родителя, реализовывать интерфейс и использовать трейт. Самостоятельный пример находится в [файле 05](code/demos/05_traits.php).

### Чем трейт не является

Трейт не создаёт новый тип объекта. Нельзя написать `new HasDeliveryStatus()` или использовать `HasDeliveryStatus $delivery` как тип параметра. Подключение `use HasDeliveryStatus` также не делает классы реализациями какого-либо интерфейса. Если другим функциям нужно гарантированно получать статус, можно отдельно объявить интерфейс `HasStatus` с методом `status(): string` и явно реализовать его в соответствующих классах.

В один класс можно подключить несколько трейтов. Если они содержат методы с одинаковым именем, конфликт придётся разрешать явно через `insteadof` или `as`[^4]. У трейтов также есть риск скрытых зависимостей: методы могут рассчитывать на свойства и другие методы конкретного класса. Поэтому их лучше применять к небольшому, понятному и действительно повторяющемуся поведению.

В нашей главе получились три разные задачи: интерфейс гарантирует методы, абстрактный класс даёт общий алгоритм, трейт переносит готовый код. Но ни один из них сам по себе не отвечает на вопрос, как _собрать один объект из других_. Эту задачу решает композиция.

## Композиция: заказ как сочетание независимых частей

### Почему наследование приводит к лишним классам

Представим страницу оформления заказа. Покупатель выбирает одну из четырёх доставок и один из двух способов оплаты:

- _Доставка_. Курьер, почта, самовывоз или экспресс.
- _Оплата_. Картой без комиссии или наличными при получении с комиссией 20 лей.

Можно попытаться представить каждую комбинацию собственным классом заказа: `CourierCardOrder`, `CourierCashOrder`, `PostCardOrder` и так далее. Для четырёх доставок и двух способов оплаты нужно восемь классов. При добавлении третьего способа оплаты получится уже двенадцать. В каждом таком классе часть логики неизбежно повторится.

Причина в неверно выбранном отношении. Заказ не _является разновидностью_ доставки или оплаты; он _использует_ выбранную доставку и оплату. Эти две части можно менять независимо.

**Композиция (composition)** - способ построить объект из других объектов, которым он поручает отдельные задачи. В нашем случае заказ использует объекты доставки и оплаты, не наследуя их код.

### Отдельный интерфейс для оплаты

Доставки уже реализуют `DeliveryMethod`. Для оплаты понадобится похожий контракт `PaymentMethod`. Этот интерфейс требует название и метод `fee()`, который рассчитывает комиссию.

```php
interface PaymentMethod
{
    public function title(): string;
    public function fee(int $amount): int;
}

final class CardPayment implements PaymentMethod
{
    public function title(): string { return 'Картой'; }
    public function fee(int $amount): int { return 0; }
}

final class CashPayment implements PaymentMethod
{
    public function title(): string { return 'Наличными при получении'; }
    public function fee(int $amount): int { return 20; }
}
```

Это учебные правила. Комиссия за наличные у нас фиксирована. В реальном приложении метод мог бы учитывать условия платёжного сервиса, а его фактическое выполнение потребовало бы отдельного взаимодействия с платёжной системой. Здесь `fee()` лишь рассчитывает число и не списывает деньги.

### Класс `Order` делегирует расчёты

Составим минимальный учебный заказ. Пока нам не нужна отдельная корзина: сумма товаров уже известна и передаётся в конструктор числом. Заказ также получает два объекта - выбранную доставку и оплату.

```php
final class Order
{
    public function __construct(
        private int $goodsTotal,
        private DeliveryMethod $delivery,
        private PaymentMethod $payment,
    ) {}

    public function goodsTotal(): int
    {
        return $this->goodsTotal;
    }

    public function deliveryCost(): int
    {
        return $this->delivery->cost($this->goodsTotal);
    }

    public function paymentFee(): int
    {
        return $this->payment->fee($this->goodsTotal + $this->deliveryCost());
    }

    public function total(): int
    {
        return $this->goodsTotal + $this->deliveryCost() + $this->paymentFee();
    }
}
```

Проследим, как рассчитывается итоговая сумма:

1. `goodsTotal()` возвращает сумму товаров, переданную при создании заказа.
2. `deliveryCost()` обращается к объекту доставки. Класс `Order` не проверяет, курьер это или экспресс.
3. `paymentFee()` передаёт объекту оплаты сумму товаров вместе с доставкой.
4. `total()` складывает товары, доставку и комиссию.

Например, отправление содержит товары на 736 лей. Курьер стоит 50 лей, а оплата наличными добавляет комиссию 20 лей:

```php
$order = new Order(736, new CourierDelivery(), new CashPayment());
echo $order->total(); // 806
```

При других вариантах доставки и оплаты меняются только объекты, которые мы передаём в конструктор:

| Доставка | Оплата    | Товары | Доставка | Комиссия | Итого |
| -------- | --------- | -----: | -------: | -------: | ----: |
| Курьер   | Картой    |    736 |       50 |        0 |   786 |
| Курьер   | Наличными |    736 |       50 |       20 |   806 |
| Экспресс | Картой    |    736 |      120 |        0 |   856 |
| Экспресс | Наличными |    736 |      120 |       20 |   876 |

Здесь один класс `Order` работает со всеми четырьмя комбинациями. В нём не появляется новое условие при добавлении ещё одного способа доставки. Попробуйте [пример 06](code/demos/06_composition.php) и проверьте, как изменится итог, если сумма товаров станет равна 1200 леям.

Передача зависимостей через конструктор называется _внедрением зависимости (dependency injection)_. Заказ не создаёт внутри себя `CourierDelivery` или `CardPayment`, поэтому мы можем подставить другую реализацию и не переписывать его методы. Во фреймворках этот подход часто используется для объединения компонентов приложения.

Это пример композиции: `Order` поручает расчёт доставки и комиссии другим объектам. Позднее сумма товаров может рассчитываться по корзине, а не храниться числом, но основной принцип от этого не изменится.

### Как выбрать способ организации кода

Разницу между механизмами удобно увидеть в одной таблице:

| Механизм          | Главный вопрос                                    | Пример                                |
| ----------------- | ------------------------------------------------- | ------------------------------------- |
| Полиморфизм       | Как одинаково работать с разными объектами?       | Вызов `cost()` у разных доставок.     |
| Интерфейс         | Какие методы обязан иметь объект?                 | `DeliveryMethod`, `PaymentMethod`.    |
| Абстрактный класс | Как разделить общий алгоритм и изменяемые шаги?   | `RegularDelivery`.                    |
| Трейт             | Как не дублировать готовые методы между классами? | `HasDeliveryStatus`.                  |
| Композиция        | Как сочетать независимые части системы?           | `Order` использует доставку и оплату. |

Композиция часто удобнее наследования для независимых частей, но не превращайте это в безусловное правило. Если приложение содержит всего два неизменных варианта и одну короткую функцию, обычный `match` может быть проще. Разделение на объекты оправдано, когда у вариантов есть собственные правила, жизненный цикл, тесты или реальные перспективы расширения.

## Статические свойства и методы: что относится к классу

### Метод, которому не нужен объект

Все методы, с которыми мы работали до этого момента, вызывались для конкретного объекта. У заказа есть `total()`, потому что у разных заказов разные суммы, способы доставки и оплаты. Но есть операции, которым состояние объекта не требуется. Например, отформатировать число `14999` как `14 999 лей` можно по одному правилу для всех расчётов доставки.

**Статический метод (static method)** - метод класса, который можно вызвать без создания объекта[^5]. Для объявления используется ключевое слово `static`, а для вызова - оператор `::`.

_Синтаксис_

```php
class ClassName
{
    public static function methodName(int $value): string
    {
        return (string) $value;
    }
}

ClassName::methodName(10);
```

_Пример_

```php
final class Price
{
    public const CURRENCY = 'лей';

    public static function format(int $amount): string
    {
        return number_format($amount, 0, ',', ' ') . ' ' . self::CURRENCY;
    }
}

echo Price::format(14999); // 14 999 лей
```

Метод `format()` получает всё необходимое через параметр `$amount`, а валюту берёт из константы класса. Поэтому для одного вызова не нужно создавать объект `new Price()`. Запись `self::CURRENCY` означает обращение к константе текущего класса.

> [!WARNING]
> В статическом методе нельзя использовать `$this`: метод не выполняется для конкретного объекта. Если для расчёта нужно состояние конкретного заказа, обычно правильнее сделать обычный метод и вызвать его у нужного объекта.

Не всякая полезная функция должна быть статическим методом. `Price::format()` здесь служит единым правилом форматирования сумм. Если формат зависит от языка или валюты пользователя, позднее может понадобиться отдельный объект форматирования с настройками. Выбор зависит от задачи.

### Статическое свойство и общее состояние

Обычное свойство принадлежит конкретному объекту. Например, у двух экземпляров `Order` могут быть разные итоговые суммы. **Статическое свойство (static property)** принадлежит классу, и при выполнении программы его значение общее для обращений через этот класс[^5].

_Синтаксис_

```php
class ClassName
{
    private static int $counter = 0;

    public static function next(): int
    {
        return ++self::$counter;
    }
}
```

После `::` у статического свойства пишется знак `$`: `self::$counter`. У константы его нет: `self::CURRENCY`.

_Пример_

```php
final class OrderCounter
{
    private static int $lastNumber = 0;

    public static function next(): int
    {
        return ++self::$lastNumber;
    }
}

echo OrderCounter::next() . "\n"; // 1
echo OrderCounter::next();         // 2
```

Два вызова обращаются к одному `$lastNumber`, поэтому следующий результат равен 2. Это полезная демонстрация того, что статическое свойство не создаётся заново для каждого объекта.

Но для настоящих номеров заказов такая схема ошибочна. В типичном PHP-приложении каждый HTTP-запрос получает новое выполнение скрипта; при следующем запросе этот счётчик начнётся сначала. Он также не решает вопрос одновременной работы нескольких процессов. Чтобы выдавать уникальные номера и помнить их после перезапуска приложения, нужен постоянный источник данных, обычно база данных с подходящим механизмом создания идентификаторов.

_Статическое свойство разделяет состояние внутри текущего выполнения, но не является хранилищем данных сайта._ Используйте его там, где это действительно нужно, и не путайте со значением, которое должно сохраняться между запросами. Практический пример можно запустить в [файле 07](code/demos/07_static.php).

## Магические константы и методы

После интерфейсов, наследования и обычных методов осталось рассмотреть несколько специальных возможностей языка. Они не заменяют изученные механизмы, но встречаются в PHP-библиотеках, фреймворках и при отладке. Их полезно узнавать и понимать, даже если в собственном коде вы используете лишь часть из них.

### Магические константы: информация о месте в программе

Иногда программе нужно знать, в каком файле или методе выполняется код. Можно вписать название вручную, но после переименования метода оно устареет.

**Магическая константа (magic constant)** - специальная константа PHP, значение которой определяется местом её использования в исходном коде[^6].

| Константа      | Значение                                   | Для чего может пригодиться            |
| -------------- | ------------------------------------------ | ------------------------------------- |
| `__LINE__`     | Номер строки исходного файла.              | Уточнить место ошибки.                |
| `__FILE__`     | Полный путь к текущему файлу.              | Работа с путями и диагностикой.       |
| `__DIR__`      | Каталог текущего файла.                    | Подключение файлов рядом со скриптом. |
| `__FUNCTION__` | Имя текущей функции или метода.            | Диагностическое сообщение.            |
| `__CLASS__`    | Имя класса в месте записи.                 | Информация о текущем классе.          |
| `__METHOD__`   | Имя метода, обычно вместе с именем класса. | Сообщение об ошибке в методе.         |

_Пример_

```php
final class Parcel
{
    public function setWeight(int $kilograms): void
    {
        if ($kilograms <= 0) {
            throw new InvalidArgumentException(
                __METHOD__ . ': вес должен быть положительным'
            );
        }
    }
}

(new Parcel())->setWeight(0);
// Исключение: Parcel::setWeight: вес должен быть положительным
```

Практически полезна и запись `__DIR__ . '/data/delivery.json'`. Она формирует путь относительно расположения исходного файла, а не относительно каталога, из которого запустили программу. Поэтому код будет надёжнее при запуске из терминала и веб-сервера.

Есть похожая по виду запись `CourierDelivery::class`: она возвращает строку с именем класса `CourierDelivery`. Это не магическая константа `__CLASS__`, значение которой зависит от того, _где в коде_ она написана. В этой главе достаточно понимать разницу, не заучивая все специальные случаи.

### Магические методы: реакция объекта на действие PHP

При создании объекта через `new` PHP автоматически вызывает `__construct()`. Это уже знакомый нам пример **магического метода (magic method)** - метода со специальным именем, который PHP вызывает при определённом действии с объектом[^7].

Обычный `title()` выполняется, когда мы сами вызываем `$delivery->title()`. А `__toString()` может сработать при записи `echo $delivery`: это уже действие PHP, с которым связан специальный метод.

Ниже рассмотрим четыре часто полезные ситуации: строковое представление, динамические свойства, объект-функцию и копирование. В конце кратко перечислим остальные методы. Эти примеры показывают возможности языка, а не набор приёмов, который обязательно применять в каждом проекте.

#### Строковое представление: `__toString()`

Предположим, нужно вывести короткое описание службы доставки. Выражение `echo $delivery` само по себе не знает, какие свойства выбрать. Метод `__toString()` задаёт строковое представление объекта.

_Синтаксис_

```php
public function __toString(): string
```

- Метод вызывается при преобразовании объекта в строку.
- Параметров у него нет.
- Результатом должна быть строка.

_Пример_

```php
final class DeliveryLabel
{
    public function __construct(private string $title, private int $price) {}

    public function __toString(): string
    {
        return $this->title . ' (' . $this->price . ' лей)';
    }
}

$delivery = new DeliveryLabel('Курьер', 50);
echo $delivery; // Курьер (50 лей)
```

PHP вызывает `__toString()` и выводит результат. Такой метод удобен для одного понятного текстового представления, но у него нет параметров для выбора языка, формата или валюты. Поэтому для разных вариантов вывода часто лучше сделать отдельные методы.

Наличие `__toString()` также не делает строку безопасной для HTML. Если название службы доставки пришло из внешних данных, перед выводом в HTML его нужно экранировать. Начиная с PHP 8.0 класс с `__toString()` автоматически реализует встроенный интерфейс `Stringable`[^7].

#### Недоступные свойства: `__get()` и `__isset()`

Обычно лучше явно объявлять свойства, чтобы PHP и редактор кода знали их имена. Однако представим класс настроек, значения которого загружаются из массива. Разработчик хочет обращаться к известной ему настройке как к `$config->currency`, хотя настоящего свойства `$currency` нет.

Для таких случаев PHP предоставляет перехват обращения к недоступному свойству. Самые важные методы:

_Синтаксис_

```php
public function __get(string $name): mixed
public function __isset(string $name): bool
```

- `__get()` вызывается при чтении недоступного свойства, получает его имя и возвращает значение.
- `__isset()` обрабатывает проверку недоступного свойства с помощью `isset()` и помогает оператору `??` решить, существует ли значение.

_Пример_

```php
final class Config
{
    public function __construct(private array $values) {}

    public function __get(string $name): mixed
    {
        if (!array_key_exists($name, $this->values)) {
            throw new InvalidArgumentException('Нет настройки: ' . $name);
        }

        return $this->values[$name];
    }

    public function __isset(string $name): bool
    {
        return isset($this->values[$name]);
    }
}

$config = new Config(['currency' => 'лей']);
echo $config->currency . "\n";                  // лей
echo $config->phone ?? 'Телефон не указан';   // Телефон не указан
```

Объект хранит значения в `$values`. Когда выполняется `$config->currency`, PHP не находит доступного свойства с таким именем и передаёт строку `'currency'` методу `__get()`. Тот находит соответствующий элемент массива. Во второй строке `??` проверяет доступность `phone`; метод `__isset()` возвращает `false`, и выводится запасная строка.

Почему здесь проверяются существование ключа и `isset()` отдельно? `array_key_exists()` отличает отсутствующий ключ от существующего со значением `null`. В то же время `isset()` считает `null` отсутствующим для выбора значения по умолчанию. Для операции `??` именно такое поведение обычно и нужно.

Есть также `__set(string $name, mixed $value): void` для записи в недоступное свойство и `__unset(string $name): void` для его удаления. Мы специально не разрешили менять настройки через `$config->currency = '...'`: такой интерфейс легко скрывает опечатки. В большинстве прикладных классов явные свойства и методы предпочтительнее.

#### Объект как функция: `__invoke()`

Представим список тарифов доставки: нужно оставить варианты со стоимостью от 50 до 150 лей. Функции `array_filter()` можно передать обычную функцию, но у нашего правила есть два настраиваемых значения - минимальная и максимальная цена. Объект позволит сохранить их и использовать одно правило многократно.

_Синтаксис_

```php
public function __invoke(int $price): bool
```

Имя `__invoke()` фиксировано, но параметры и тип результата зависят от назначения объекта.

_Пример_

```php
final class PriceRange
{
    public function __construct(private int $min, private int $max) {}

    public function __invoke(int $price): bool
    {
        return $price >= $this->min && $price <= $this->max;
    }
}

$filter = new PriceRange(50, 150);
$prices = [35, 50, 120, 250];

echo implode(', ', array_filter($prices, $filter));
// 50, 120
```

Выражение `$filter(120)` выглядит как вызов функции, но PHP выполняет метод `$filter->__invoke(120)`. Это позволяет передавать объект туда, где ожидается вызываемое значение (callback), например в `array_filter()`. Такой вариант удобен, когда правило имеет собственные настройки. Для простой одноразовой проверки достаточно обычной функции или стрелочной функции.

#### Копирование вложенных объектов: `__clone()`

Оператор `clone` создаёт новый объект, копируя его свойства. Но если свойство хранит _ссылку на другой объект_, оба экземпляра после обычного копирования продолжат использовать этот вложенный объект. Это может привести к неожиданному изменению сразу двух заказов[^8].

_Синтаксис_

```php
public function __clone(): void
```

Метод `__clone()` вызывается при клонировании и позволяет настроить копию после обычного копирования свойств.

_Пример_

```php
final class Address
{
    public function __construct(public string $city) {}
}

final class DraftOrder
{
    public function __construct(public Address $address) {}

    public function __clone(): void
    {
        $this->address = clone $this->address;
    }
}

$first = new DraftOrder(new Address('Кишинёв'));
$second = clone $first;
$second->address->city = 'Бельцы';

echo $first->address->city . "\n";  // Кишинёв
echo $second->address->city;         // Бельцы
```

Без строки `$this->address = clone $this->address` оба заказа ссылались бы на один `Address`. После изменения города во втором заказе город первого тоже стал бы Бельцами. Наш `__clone()` создаёт отдельный вложенный адрес для копии заказа.

Не нужно бездумно клонировать все вложенные объекты: некоторые объекты предназначены для общего использования или являются неизменяемыми. Важен вопрос, _должно ли изменение копии влиять на оригинал_. Для адреса в учебном примере ответ - нет.

#### Остальные магические методы и ограничения

В PHP существуют и другие специальные методы. Они полезны в библиотеках и инструментах, но для учебной задачи расчёта доставки не обязательны:

| Метод                              | Когда вызывается                                           | Что важно понимать                                                                             |
| ---------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `__set()`                          | При записи в недоступное свойство.                         | Можно проверить или запретить запись.                                                          |
| `__unset()`                        | При удалении недоступного свойства через `unset()`.        | Может управлять удалением внутреннего значения.                                                |
| `__call()`                         | При вызове отсутствующего или недоступного метода объекта. | Позволяет перенаправить вызов, но скрывает доступные методы от читателя кода.                  |
| `__callStatic()`                   | При вызове недоступного статического метода.               | Похож на `__call()`, но для статического вызова.                                               |
| `__destruct()`                     | При уничтожении объекта.                                   | Подходит для некоторых завершающих действий, но не должен заменять надёжное сохранение заказа. |
| `__debugInfo()`                    | При выводе через `var_dump()`.                             | Позволяет настроить отладочное представление, например не выводить чувствительные поля.        |
| `__serialize()`, `__unserialize()` | При сериализации и восстановлении объекта.                 | Используются для управления представлением объекта при сериализации.                           |

Все названия магических методов зарезервированы PHP. За исключением `__construct()`, `__destruct()` и `__clone()` они должны быть объявлены как `public`[^7].

Сами по себе магические методы не делают класс лучше. Из-за `__get()` редактор может не знать, существует ли `$config->currency`; из-за `__call()` опечатка в названии метода может обнаружиться позднее. Используйте их там, где нужен именно особый механизм PHP, а не вместо обычных свойств и методов. Выполнение четырёх основных примеров можно проверить в [файле 08](code/demos/08_magic.php).

## Практический пример: оформление заказа

В качестве заключительного примера соберём MiniShop - небольшой учебный интернет-магазин. Здесь применим изученные механизмы на странице оформления заказа. Корзина уже содержит две компьютерные мыши по 299 лей, коврик за 89 лей и подарочную упаковку за 49 лей. Сумма товаров составляет 736 лей.

Сценарий состоит из нескольких понятных шагов:

1. Страница получает от пользователя код доставки и код оплаты.
2. Код `match` преобразует допустимые строки в объекты нужных классов.
3. В этом примере класс `Order` расширен: вместо готовой суммы товаров он получает объект `Cart`, а также доставку и оплату.
4. Методы заказа вызывают соответствующие расчёты и возвращают итог.
5. Страница показывает результат, не реализуя внутри HTML правила доставки и комиссии.

Заметьте, что `match` никуда не исчез. Теперь он решает узкую задачу _выбрать объект по коду_, а не содержит все бизнес-правила доставки. Это нормальное использование конструкции, а не отказ от неё в пользу ООП.

### Выбор объектов по коду

Сервер получает строки вроде `'courier'` и `'cash'`. Их нужно проверить до создания заказа. Следующий фрагмент использует функции из полного примера:

```php
function makeDelivery(string $code): DeliveryMethod
{
    return match ($code) {
        'courier' => new CourierDelivery(),
        'post' => new PostDelivery(),
        'pickup' => new PickupDelivery(),
        'express' => new ExpressDelivery(),
        default => throw new InvalidArgumentException('Неизвестный способ доставки'),
    };
}

function makePayment(string $code): PaymentMethod
{
    return match ($code) {
        'card' => new CardPayment(),
        'cash' => new CashPayment(),
        default => throw new InvalidArgumentException('Неизвестный способ оплаты'),
    };
}
```

Выходной тип каждой функции - интерфейс. Это означает, что вызывающий код может пользоваться требуемыми методами и не зависит от класса, выбранного внутри. Ветка `default` нужна обязательно: если посетитель передаст неизвестный код, сервер не должен молча назначать неверный тариф.

### Расчёт заказа

Проверим оформление для курьера и оплаты наличными. В следующем фрагменте `makeCart()` создаёт описанную корзину, а `Price::format()` выводит суммы в леях.

```php
$cart = makeCart();
$delivery = makeDelivery('courier');
$payment = makePayment('cash');

$order = new Order($cart, $delivery, $payment);

echo 'Товары: ' . Price::format($order->goodsTotal()) . "\n";
echo 'Доставка: ' . Price::format($order->deliveryCost()) . "\n";
echo 'Оплата: ' . Price::format($order->paymentFee()) . "\n";
echo 'Итого: ' . Price::format($order->total());
// Товары: 736 лей
// Доставка: 50 лей
// Оплата: 20 лей
// Итого: 806 лей
```

Если заменить `'courier'` на `'express'`, итог увеличится до 876 лей при оплате наличными. Если выбрать `'pickup'` и `'card'`, итог станет равен стоимости товаров, 736 леям. При этом ни один метод `Order` не меняется: разные реализации выбираются через интерфейсы, а сам заказ сочетает их с помощью композиции.

Обратите внимание, что здесь `Order` отличается от упрощённой версии в разделе о композиции: сумма товаров теперь вычисляется корзиной. Полные объявления `Cart`, `Product` и `Order` можно увидеть в коде приложения.

В самостоятельном [примере 09](code/demos/09_checkout.php) значения `$deliveryCode` и `$paymentCode` заданы в начале сценария. Поменяйте их, запустите программу ещё раз и сравните итог:

```bash
php code/demos/09_checkout.php
```

### Веб-страница и границы учебного примера

В архиве есть также самостоятельная [страница `code/checkout.php`](code/checkout.php). В одном файле находятся все классы и HTML-форма с двумя выпадающими списками и кнопкой "Пересчитать". При отправке формы в адресе страницы появляются параметры `delivery` и `payment`. Скрипт проверяет, что оба значения являются строками, а функции выбора не допускают неизвестных кодов. > В учебном примере товары заранее добавлены в корзину и не сохраняются между запросами. Мы демонстрируем организацию PHP-кода, а не полноценную систему оформления заказов. Реальному магазину также потребуются база данных, проверка наличия товаров, защита запросов и интеграция с платёжным провайдером.

Инструкция по запуску находится в [README к коду](code/README.md). Все девять примеров и веб-страница работают отдельно: файлы не нужно связывать друг с другом. Полезно сначала выполнить примеры 01-09, затем открыть HTML-страницу и попробовать выбрать каждый из четырёх способов доставки.

## Типичные ошибки и как их распознать

| Ситуация                                                                                                  | Почему возникает                                                     | Что изменить                                                                |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| У класса есть `cost()` и `title()`, но функция не принимает его как `DeliveryMethod`.                     | Класс не объявил `implements DeliveryMethod`.                        | Явно реализовать интерфейс.                                                 |
| Реализация метода интерфейса объявлена `private` или возвращает несовместимый тип.                        | Не соблюдены требования контракта.                                   | Сделать метод `public` и согласовать сигнатуру.                             |
| Код пытается выполнить `new RegularDelivery()`.                                                           | Абстрактные классы нельзя создавать напрямую.                        | Создавать конкретный класс, например `CourierDelivery`.                     |
| Курьер случайно начинает брать плату при заказе на 1200 лей.                                              | Общее правило скопировано в несколько мест и изменено не везде.      | Хранить общий алгоритм в `RegularDelivery` и проверять порог тестом.        |
| Класс использует `HasDeliveryStatus`, но не принимается функцией, которая ожидает определённый интерфейс. | Трейт не делает классы наследниками или реализациями интерфейса.     | Для общего типа использовать интерфейс.                                     |
| Возникают восемь почти одинаковых классов заказа.                                                         | Независимые доставки и оплаты представлены комбинациями наследников. | Хранить объекты доставки и оплаты внутри `Order`.                           |
| В статическом методе используется `$this`.                                                                | Статический метод не привязан к экземпляру класса.                   | Работать с аргументами и статическими членами либо сделать метод обычным.   |
| Номера заказов повторяются после обновления страницы.                                                     | Статический счётчик не хранится между независимыми HTTP-запросами.   | Использовать постоянное хранилище и корректную выдачу ID.                   |
| После `clone` изменение адреса копии меняет адрес оригинала.                                              | Вложенный изменяемый объект остался общим.                           | Если требуется независимость, скопировать вложенный объект в `__clone()`.   |
| Опечатка в виртуальном свойстве обнаруживается поздно.                                                    | `__get()` скрывает список допустимых свойств.                        | Предпочитать объявленные свойства и методы, а при динамике проверять имена. |

## Резюме

- Полиморфизм позволяет одинаково вызывать методы разных объектов, не проверяя их конкретный класс при каждом вызове.
- Интерфейс задаёт обязательные возможности и даёт общий тип для взаимозаменяемых реализаций.
- Абстрактный класс позволяет вынести общий алгоритм и требовать от наследников реализацию отдельных шагов.
- Трейт переносит готовое поведение между классами, но не создаёт новый тип объекта.
- Композиция объединяет независимые части: заказ использует выбранные доставку и оплату.
- Статические члены относятся к классу, но статические свойства не заменяют постоянное хранилище веб-приложения.
- Магические константы и методы упрощают отдельные задачи PHP, однако требуют внимательного и умеренного применения.
- Качественное ООП начинается с конкретной проблемы; не каждую функцию `match` или повторяющуюся строку нужно заменять новой иерархией классов.
